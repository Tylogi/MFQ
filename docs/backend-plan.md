# MFQ C++ 服务端迁移计划

目标设计见 [C++ 服务端目标架构](backend-architecture.md)。阶段 1 的功能项已完成并通过
Linux 验收；Windows/macOS 尚待验证。阶段 2 已实现模型目录部分，真实推理链路仍待接入。
Studio 和发布包继续使用现有入口，待迁移功能闭环后再切换。

| 阶段 | 当前成果与验证 | 下一步 |
| --- | --- | --- |
| 阶段 1：服务基础设施 | Linux 七组、951 项专项检查通过；原生回归 34 项通过 | Windows/macOS 验收 |
| 阶段 2：同进程模型与推理 | 模型目录浏览、注册、元数据与重启恢复；Linux 两组、112 项检查通过 | Engine/Scheduler 装配、真实模型加载、流式推理、取消和卸载 |

## 1. 实施原则

- 工作在 `refactor/backend`，承接 `refactor/cuda` 的 `cpp_runtime` → `csrc` 调整，
  不在两个分支分别重命名同一棵源码树。
- 保留 Scheduler/Engine 分工和基于 `RequestId` 的记录交接；不借服务迁移重写整套引擎。
- 每个阶段完成可使用的功能链路，包括入口、调用方、持久化、取消和错误处理。
  空路由、占位返回和只启动成功的服务不算功能迁移完成。
- 内部接口可以整理；公共产品行为、数据完整性、权限和执行校准不能因重写而丢失。
- 不把现有 Python 文件一对一翻译成 C++，也不预建无实际消费者的抽象和配置。
- Studio 与正式发布在功能闭环后切换，不能仅凭原生服务能监听端口就替换旧服务。

## 3. 阶段 1：原生服务入口与基础设施

目标位置为 `csrc/apps/server_main.cpp`、`server/server.*`、`api/`、`auth/` 和 `storage/`。

- [x] 建立原生服务构建目标、CLI 配置、日志、资源定位与退出处理。
- [x] 复用现有 HTTP/JSON 组件，提供健康、实例身份、监听与静态资源功能。
- [x] 迁移数据目录实例锁、Studio 身份核对和 stdin 关闭时退出的生命周期约定。
- [x] 迁移鉴权策略、密钥、权限、HTTP/WS 认证及非回环监听的保护规则。
- [x] 接入 SQLite 原生接口与数据库版本管理；保留现有数据，不以空库替代迁移。
- [x] 明确服务模块的装配和停止顺序，避免持有数据库事务等待推理或网络操作。

上述功能项的验收范围为 Linux，跨平台验收单独跟踪：

- [x] Linux：服务专项验收及原生回归。
- [ ] Windows：构建、实例锁、鉴权持久化、SQLite 和退出清理。
- [ ] macOS：构建、实例锁、鉴权持久化、SQLite 和退出清理。

第一批实现位于 `cpp_runtime/apps/server_main.cpp` 和 `cpp_runtime/server/`，
暂不另行重命名 `csrc`。`mfq-server` 可在关闭全部 GPU 后端和旧推理通信层时构建，
提供 `/health`、`/health/identity`、显式 `--web-root` 静态文件及 SPA 回退。
实例身份和锁文件与现有 Python 服务使用同一约定；重复启动、端口冲突、stdin EOF、
SIGINT/SIGTERM 退出及路径校验已纳入进程测试，当前仅在 Linux 验证。
构建与运行方式见 [原生入口说明](../cpp_runtime/README.md#native-server-bootstrap)。

鉴权入口已支持策略修改、密钥创建/列出/撤销/轮换、scope/role 权限及有效期，
只持久化密钥哈希。HTTP Bearer、Anthropic `X-Api-Key` 和 WebSocket 升级前的
`access_token` 校验共用权限入口，并处理 Studio CORS 预检。非回环监听必须启用
有效鉴权；保存的策略优先于环境变量，网络监听期间不能关闭鉴权。

SQLite 直接使用原生接口，默认读取 `server.sqlite3`，兼容已有
`mfq-server.sqlite3`，也可用 `--db` 指定。两套服务共用 SQL schema；原生服务支持
1–18 版数据库迁移到 19，迁移失败回滚，未知版本和损坏数据库拒绝启动。
本次重写沿用现有 19 版，没有新增数据库版本。已有 19 版校验鉴权所需结构并启用
WAL，跳过 schema 初始化和版本重写；旧库升级用于继续使用原有数据。
装配顺序为实例锁、鉴权策略、模型目录配置、数据库和 HTTP；退出先停止并等待 HTTP 请求，
再关闭数据库和释放实例锁。数据库锁只覆盖查询与更新，不跨网络操作持有。

服务测试已改为 C++ 可执行程序，由 CTest 运行，无 Python 解释器或测试框架依赖。
覆盖 CLI/生命周期、锁与端口、静态资源、策略与协议、权限与网络监听、带待处理工作
退出、数据库迁移七组场景。1–18 版标记的旧库包含实际会话、消息、回复、任务、
密钥和生成预设记录，验证迁移后的数据、缺列补齐、预设 nullable 约束和失败回滚。
未知库不覆盖；当前版本缺失鉴权字段时拒绝启动。退出测试包括数据库暂时被占用、
提交中的密钥写入、HTTP 队列中的不完整连接以及锁的重新获取。
专项验收可独立执行：`ctest --test-dir build/native-server -L stage1 --output-on-failure`。
旧推理通信层关闭和开启时均可构建；已有 prefix-cache、runtime-transport 和
runtime-profile 检查通过。Linux 阶段一专项七组、951 项检查通过；启用旧通信层的
完整原生回归共 34 项通过。回归编译中修正了模型库的 C++20 标准声明，使其与
已有公共头文件使用的 `requires` 一致。

第一批的原生架构边界断言为 66 项中 61 项通过，5 项 CUDA 存量断言失败，
失败涉及的后端源码和测试均未改动。当前仅在 Linux 验证；Windows、macOS、
GPU 模型运行与完整 Python 服务测试尚未验证。

模型目录的后续实现见阶段 2；其他管理、推理和实时 WebSocket 功能仍待迁移，Studio 和发布入口尚未切换。

退出条件：原生服务可以在没有加载模型时完成管理入口、身份和持久化功能；
配置或端口冲突能正确失败，退出可以释放实例锁。此时不宣称完整替代 Python 服务。

## 4. 阶段 2：同进程模型实例与第一条真实推理链路

目标位置为 `server/models/`、模型源/格式模块和现有 Scheduler、Engine 的公开接口。

- [ ] 迁移本地模型发现、目录注册、配置读取、加载参数与能力信息。
- [ ] 通过公开后端工厂创建 Engine，为每个模型实例配套创建 Scheduler。
- [ ] 用直接调用替换本地 runtime 可执行程序、私有端口、握手和客户端。
- [ ] 接入模型实例路由、加载卸载、内存预算和失败回收，复用实际资源所有者的账本。
- [ ] 补齐原生 tokenizer 资产读取或转换，不能依赖 Python 预先生成 GGUF 才能加载。
- [ ] 核对准入、输入转移、取消、终止和清理的交接，收敛已准入请求的异常结束权。
- [ ] 保留请求数、输入字节、输出字节/事件和媒体峰值的约束，不引入无界队列。

当前已接入本地模型目录的列表、浏览、注册及按模型 ID 查询所在目录的 HTTP 链路。
默认目录为 `DATA_DIR/models`，可重复指定 `--model-dir`，或使用
`MFQ_SERVER_MODEL_DIRS`。注册结果沿用 `.mfq-files.json`，重启后可恢复。
复用原生 MFQ/Safetensors 读取器报告真实文件、张量、dtype 和声明的上下文容量，
扫描不读取完整权重。缺失分片与损坏文件列为不可用；同格式重名返回冲突，
注册失败保留原索引和快照。目录接口需要模型管理权限，模型列表不公开文件路径。

C++ 集成测试已覆盖这些接口、目录 ID 生命周期、Unicode 路径、多根目录与环境变量
优先级、重启恢复、重复注册、重名回滚、损坏索引、索引写入大小和扫描深度限制。
专项验收为两组、112 项检查：`ctest --test-dir build/native-server -L stage2 --output-on-failure`。
目前刷新为同步扫描，慢盘会延迟目录请求；扫描数量和深度、索引大小均有上限。
Engine/Scheduler 装配、加载参数和能力校验尚未接入，目录中所有模型均明确返回
`loadable: false`，因此本阶段第一项仍未整体勾选。

本阶段第一个可验收结果：

```text
原生服务启动 → 注册本地模型 → 创建 Engine + Scheduler
→ OpenAI 流式推理 → 取消请求 → 卸载模型 → 正常退出
```

退出条件：这条链路使用真实模型，不调用 Python，不启动本地推理子进程；
慢消费者、取消或异常不应导致提前释放资源或无法卸载。相关推理修正与 CUDA 分支
协调，避免两个分支分别维护不同的取消/清理规则。

## 10. 验收与删除门槛

后续实施应按改动范围选择检查，不在纯讨论或源码审查时擅自启动构建与测试。
需要覆盖的行为包括：

| 范围 | 应验证的关键行为 |
| --- | --- |
| 请求交接 | 排队取消、准入后取消、超时、慢消费者、单一终止事件、清理后终止 |
| 故障恢复 | 加载失败、部分资源分配后失败、执行故障、reload、shutdown |
| 公共协议 | 参数约束、权限、错误、工具调用、reasoning、SSE/WS 与断连 |
| 持久化 | 现有数据库读取、迁移失败、版本冲突、幂等、会话与任务的中断恢复 |
| 产品依赖 | tokenizer、媒体、工具、Studio 和发布包在没有 Python 时运行 |
| 平台与资源 | 目标后端的真实模型、动态库与媒体资源、有界内存和多实例预算 |

原生规则检查、接口检查与真实硬件验证各自说明范围，不能用替身实现证明 GPU 或
媒体功能已经完成。旧路径删除前，必须迁完消费者、数据处理、文档和发布入口；
未验证的能力与尚未决定的范围保留明确记录。
