# MFQ C++ 服务端迁移计划

目标设计见 [C++ 服务端目标架构](backend-architecture.md)。阶段 1 已开始实施；
尚未勾选的检查项仍是后续工作的退出条件，不能据此切换产品入口。

## 1. 实施原则

- 工作在 `refactor/backend`，承接 `refactor/cuda` 的 `cpp_runtime` → `csrc` 调整，
  不在两个分支分别重命名同一棵源码树。
- 保留 Scheduler/Engine 分工和基于 `RequestId` 的记录交接；不借服务迁移重写整套引擎。
- 每个阶段完成可使用的功能链路，包括入口、调用方、持久化、取消和错误处理。
  空路由、占位返回和只启动成功的服务不算功能迁移完成。
- 内部接口可以整理；公共产品行为、数据完整性、权限和执行校准不能因重写而丢失。
- 不把现有 Python 文件一对一翻译成 C++，也不预建无实际消费者的抽象和配置。
- Studio 与正式发布在功能闭环后切换，不能仅凭原生服务能监听端口就替换旧服务。

## 2. 阶段 0：盘点和承接目录调整

涉及当前的 `mfq/server/`、`mfq/commands/`、`mfq/runtime/`、`MFQStudio/`、
`packaging/`、`pyproject.toml`、CI 和原生构建入口。

- [ ] 以 OpenAPI、实际路由、前端调用、CLI、WebSocket 和桌面握手建立迁移清单。
- [ ] 每项记录现有行为、调用方、持久化、Python 依赖、目标模块和验收方式。
- [ ] 区分产品运行依赖与独立研究脚本；列清尚未确定的离线工具范围。
- [ ] 协调并集成可审查的 `csrc` 目录调整，明确哪些推理接口仍在 CUDA 分支演进。
- [ ] 盘点需要保留的外部协议与远端/沙箱通信，以及可以删除的本地推理 IPC。
- [ ] 为现有 CLI 参数明确保留、替换或移除结果，并同步找到全部调用方。

退出条件：功能清单可追踪到源码和消费者；目录基线明确。未迁移能力有明确归属，
不能通过漏记接口或只统计 OpenAPI 操作数缩小范围。

## 3. 阶段 1：原生服务入口与基础设施

目标位置为 `csrc/apps/server_main.cpp`、`server/server.*`、`api/`、`auth/` 和 `storage/`。

- [x] 建立原生服务构建目标、CLI 配置、日志、资源定位与退出处理。
- [x] 复用现有 HTTP/JSON 组件，提供健康、实例身份、监听与静态资源功能。
- [x] 迁移数据目录实例锁、Studio 身份核对和 stdin 关闭时退出的生命周期约定。
- [ ] 迁移鉴权策略、密钥、权限、HTTP/WS 认证及非回环监听的保护规则。
- [ ] 接入 SQLite 原生接口与数据库版本管理；保留现有数据，不以空库替代迁移。
- [ ] 明确服务模块的装配和停止顺序，避免持有数据库事务等待推理或网络操作。

第一批实现位于 `cpp_runtime/apps/server_main.cpp` 和 `cpp_runtime/server/`，
暂不另行重命名 `csrc`。`mfq-server` 可在关闭全部 GPU 后端和旧推理通信层时构建，
提供 `/health`、`/health/identity`、显式 `--web-root` 静态文件及 SPA 回退。
实例身份和锁文件与现有 Python 服务使用同一约定；重复启动、端口冲突、stdin EOF、
SIGINT/SIGTERM 退出及路径校验已纳入进程测试，当前仅在 Linux 验证。
构建与运行方式见 [原生入口说明](../cpp_runtime/README.md#native-server-bootstrap)。

本批验证：旧推理通信层关闭和开启时均可构建；12 项原生服务进程测试、
已有 prefix-cache、runtime-transport 和 runtime-profile 检查通过。
额外执行现有原生架构边界断言，66 项中 61 项通过，5 项 CUDA 存量断言失败，
失败涉及的后端源码和测试均未改动。完整 pytest 未执行，当前环境缺少 pytest/Pydantic；
Windows、macOS 与 GPU 模型运行尚未验证。

鉴权和 SQLite 尚未接入，当前仅允许 `127.0.0.1`、`::1` 监听，
不读写现有数据库、不提供管理或推理接口，也尚未切换 Studio 和发布入口。

退出条件：原生服务可以在没有加载模型时完成管理入口、身份和持久化功能；
配置或端口冲突能正确失败，退出可以释放实例锁。此时不宣称完整替代 Python 服务。

## 4. 阶段 2：同进程模型实例与第一条真实推理链路

目标位置为 `server/models/`、模型源/格式模块和现有 Scheduler、Engine 的公开接口。

- [ ] 迁移本地模型发现、目录注册、配置读取、加载参数与能力信息。
- [ ] 通过公开后端工厂创建 Engine，为每个模型实例配套创建 Scheduler。
- [ ] 用直接调用替换本地 runtime 可执行程序、私有端口、握手和客户端。
- [ ] 接入模型实例路由、加载卸载、内存预算和失败回收，复用实际资源所有者的账本。
- [ ] 补齐原生 tokenizer 资产读取或转换，不能依赖 Python 预先生成 GGUF 才能加载。
- [ ] 核对准入、输入转移、取消、终止和清理的交接，收敛已准入请求的异常结束权。
- [ ] 保留请求数、输入字节、输出字节/事件和媒体峰值的约束，不引入无界队列。

本阶段第一个可验收结果：

```text
原生服务启动 → 注册本地模型 → 创建 Engine + Scheduler
→ OpenAI 流式推理 → 取消请求 → 卸载模型 → 正常退出
```

退出条件：这条链路使用真实模型，不调用 Python，不启动本地推理子进程；
慢消费者、取消或异常不应导致提前释放资源或无法卸载。相关推理修正与 CUDA 分支
协调，避免两个分支分别维护不同的取消/清理规则。

## 5. 阶段 3：公共推理接口与聊天持久化

及其实际消费者。

- [ ] 迁移 OpenAI/Anthropic 的模型列表、生成、计数及错误和流式事件语义。
- [ ] 迁移对话、消息、分支、回复、预设、导入导出、幂等和版本冲突处理。
- [ ] 将 Scheduler 结果连接到协议输出和持久化，不在服务层再建一套推理排队器。
- [ ] 保留取消、客户端断连、重复请求和服务重启后的回复状态处理。
- [ ] 迁移 OpenAPI 及必要的公共契约；解除 FastAPI/Pydantic 的契约生成依赖。

退出条件：同一服务重启后能继续访问已有会话，聊天与两类兼容 API 完整可用；
协议输出、数据库状态和 Engine 完成状态一致。

- [ ] 迁移任务创建、执行、进度事件、取消、重试、删除和中断恢复。
- [ ] 接入模型仓库元数据、文件选择、分片解析、下载续传、完整性校验和下载目录。
- [ ] 验证 HTTPS、代理、证书、重定向与范围请求，再确定下载实现和依赖。

- [ ] 将通用解码与模型预处理语义分开，复用既有原生媒体和模型实现。
- [ ] 迁移 WebSocket 实时流程；协调 Duplex 生成纳入统一请求、取消和背压链路。
- [ ] 迁移数据集、评分、基准和结果对比，复用现有原生评测能力。
- [ ] 对产品中提供的量化、校准、组件安装等任务逐项替换 Python 依赖。
- [ ] 保留需要隔离的评测程序及其沙箱约束，不把不可信执行塞进服务进程。

退出条件：迁移清单中的媒体和产品工具可用，后台路径不再调用 Python；缺少原生
实现的产品功能仍是切换阻塞项，不能通过空成功或静默禁用算作完成。
独立研究与训练脚本继续按待确认范围处理。

## 10. 验收与删除门槛

后续实施应按改动范围选择检查，不在纯讨论或源码审查时擅自启动构建与测试。
需要覆盖的行为包括：

| 范围 | 应验证的关键行为 |
| --- | --- |
| 请求交接 | 排队取消、准入后取消、超时、慢消费者、单一终止事件、清理后终止 |
| 故障恢复 | 加载失败、部分资源分配后失败、执行故障、reload、shutdown |
| 公共协议 | 参数约束、权限、错误、工具调用、reasoning、SSE/WS 与断连 |
| 持久化 | 现有数据库读取、迁移失败、版本冲突、幂等、会话与任务的中断恢复 |
| 产品依赖 | tokenizer、媒体、工具、Studio 和发布包在没有 Python 时运行 |
| 平台与资源 | 目标后端的真实模型、动态库与媒体资源、有界内存和多实例预算 |

原生规则检查、接口检查与真实硬件验证各自说明范围，不能用替身实现证明 GPU 或
媒体功能已经完成。旧路径删除前，必须迁完消费者、数据处理、文档和发布入口；
未验证的能力与尚未决定的范围保留明确记录。
